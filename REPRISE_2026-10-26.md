## Clarification WASAPI — après lancement de la répartition des travaux

L'utilisateur a demandé pourquoi WASAPI n'avait pas de dépôt spécifique,
puis demandé de conserver l'explication suivante :

- Le maintien de WASAPI dans TimoxVAudioEngine est **provisoire pour la
  première extraction**. Il conserve le comportement existant pendant la
  séparation des dépôts ; il ne tranche pas l'organisation définitive.
- Un dépôt **TimoxVWasapi fournissant une bibliothèque** est une option
  cohérente : il posséderait l'accès Windows aux périphériques et aux flux,
  tandis que le moteur garderait leur raccordement au graphe audio.
- Un dépôt autonome **n'impose ni programme ni service séparé**. Une
  bibliothèque peut rester dans le même processus que le moteur, sans
  transport audio interprocessus supplémentaire.
- Le gestionnaire actuel dépend du routage du moteur et de la durée de vie
  des buffers/callbacks. L'extraction de la bibliothèque nécessite donc une
  frontière explicite et sa validation, pas seulement un déplacement de
  fichiers.
- Le choix module ou dépôt bibliothèque reste ouvert. Ne pas interpréter
  l'accord sur cette explication comme un choix définitif d'architecture.

Plan de répartition :
[`docs/plans/2026-10-26-repartition-depots.md`](docs/plans/2026-10-26-repartition-depots.md).

## Modèle objet à poursuivre

- Deux agrégats proposés pour la lecture du modèle API : `AudioConfiguration`
  (souhaité/persisté) et `AudioEngine` (appliqué/observé). L’inventaire système
  est une observation référencée, pas une troisième racine métier.
- **`VSSCClient` appartient à TimoxVSSC** : identité générique dans le graphe,
  indépendante du transport. Types à distinguer : client ASIO adhérent, client
  WASAPI endpoint, client WASAPI process-copy et client PWAR.
- Pour une copie WASAPI, le processus choisi est le scope source ; le client du
  graphe est le flux distinct créé par TimoxVSSC. Le processus ne devient pas
  lui-même client ASIO et son API audio n’est pas déduite.
- TimoxVAudioEngine expose les ressources techniques (sessions ASIO, ponts
  WASAPI, ports et mesures). Son API actuelle ne publie pas encore d’identité
  `VSSCClient` ni de mapping vers les clients du graphe. Le code de cette API
  réside encore dans le dépôt TimoxVasio.
- Le client ASIO prouve l’ouverture du pilote et son attachement. Les ports
  alloués et callbacks sont observables ; ils ne prouvent pas un signal audible.
  L’API ne publie actuellement que PID et nom de processus.
- Conserver la distinction **desired / applied / observed**. La configuration
  disque n’a pas de révision persistée ; `expectedConfigurationRevision` est
  optionnel ; l’API ne publie pas de révision appliquée distincte.

Proposition poussée dans le dépôt TimoxVasio :
[`docs/superpowers/specs/2026-10-26-timox-object-model-design.md`](docs/superpowers/specs/2026-10-26-timox-object-model-design.md).
Les commits de revue précédents sont `fcf84d7` et `e374f58` sur la branche
`ccr-d306084d-ieaii9`. Une correction de nommage (`TVSD` → `TimoxVSSC`, client
